# Teamboard — правила проекта для ИИ-агентов

Веб-приложение для управления задачами команды (тестовое задание). Интерфейс на русском.
Подробно об устройстве — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), о причинах решений — в [docs/DECISIONS.md](docs/DECISIONS.md).

@AGENTS.md

## Стек

- Next.js 16 (App Router, Cache Components включены), React 19, TypeScript strict
- Tailwind CSS 4; свои компоненты в `src/components/ui` на примитивах Radix; иконки lucide-react;
  перетаскивание — dnd-kit; тосты — sonner; тема — next-themes; шрифт Inter из npm (локально)
- PostgreSQL + Drizzle ORM; авторизация — Better Auth (вход по логину и паролю)
- Zod 4 — проверка всех входных данных
- Vitest (модульные и интеграционные, база — PGlite в памяти), Playwright (сквозные)
- Docker (самодостаточная сборка `output: "standalone"`), GitHub Actions

## Команды

| Команда                         | Что делает                                                       |
| ------------------------------- | ---------------------------------------------------------------- |
| `pnpm dev`                      | Режим разработки (нужен `.env.local`, миграции применяются сами) |
| `pnpm check`                    | Всё перед коммитом: типы, линтер, формат, тесты с покрытием      |
| `pnpm test` / `pnpm test:watch` | Модульные и интеграционные тесты                                 |
| `pnpm test:e2e`                 | Сквозные тесты (нужна база `teamboard_e2e`)                      |
| `pnpm build && pnpm start`      | Боевая сборка и запуск                                           |
| `pnpm db:generate`              | Создать миграцию после изменения `src/db/schema`                 |
| `pnpm db:seed`                  | Заполнить базу демо-данными                                      |

## Слои (нарушение — ошибка линтера)

```
Интерфейс            src/app, src/features/*/components
   │  вызывает только actions.ts / queries.ts / session.ts
Граница сервера      src/features/*/server/{actions,queries,session}.ts
   │  сессия → проверка ввода (Zod) → сервис → ActionResult
Сервисы              src/features/*/server/service.ts     (правила; без базы и без Next.js)
Репозитории          src/features/*/server/repository.ts  (единственное место запросов к базе)
База                 src/db (схема, миграции, подключение)
```

Общие для сервера и браузера, без зависимостей от фреймворка: файлы верхнего уровня модуля —
`model.ts` (типы и константы), `schemas.ts` (Zod), `policy.ts` (права) — и `src/lib/*.ts`.
Зависимости идут только вниз: действия → сервис → репозиторий. Интерфейсу из `server/` доступны
ровно три файла: `actions.ts`, `queries.ts`, `session.ts`.

## Обязательные правила

1. **Права и ввод проверяет сервер.** Любое изменение — через `authedAction(name, schema, handler)`
   из `features/auth/server/authed-action.ts`. Интерфейс только прячет недоступные кнопки (`policy.ts`).
2. **Действия не бросают ошибки наружу**, а возвращают `ActionResult` (`src/lib/result.ts`).
   Сервисы бросают `AppError` из `src/lib/errors.ts` с текстом на русском.
3. **Запросы к базе — только в `repository.ts`.** Репозиторий и сервис — фабрики
   (`createXRepository(db)`, `createXService(deps)`), собираются в `server/index.ts`. В тестах — с базой в памяти.
4. **Статусы, приоритеты, лимиты** заданы один раз в `features/tasks/model.ts`. Не дублировать строки.
5. **Чтение данных на страницах** — в асинхронном компоненте внутри `<Suspense>` (требование Cache Components).
   Данные пользователей не кэшировать (`use cache` для задач не применять) — команда должна видеть свежее.
6. **Никаких внешних сервисов в браузере**: шрифты и иконки только локальные (`next/font/local`, пакеты npm).
   Проверяющие в России — CDN и Google Fonts недопустимы.
7. **Секреты — только в переменных окружения** (`src/lib/server/env.ts`). Новую переменную добавлять
   в схему там же и в `.env.example`.
8. **Тесты сначала.** Новая логика — с тестом рядом (`*.test.ts`), покрытие не ниже 80 %.
   Не говорить «работает», пока не прошёл `pnpm check`.
9. Иммутабельность, маленькие файлы и функции, без `any`, без `console` (есть `logger`).
10. Коммит после каждого рабочего шага: `<type>: <description>` (feat, fix, refactor, docs, test, chore, perf, ci).

## Особенности, о которых легко забыть

- **Next.js прячет, а не удаляет предыдущие страницы** (до трёх, через `<Activity>`). Последствия:
  состояние форм и открытых окон сохраняется — временное состояние сбрасывать в очистке `useLayoutEffect`;
  в Playwright искать элементы по роли (`getByRole`) — `getByLabel`/`getByText` находят и скрытые страницы,
  для них добавлять `.filter({ visible: true })`. Сообщения об ошибках искать внутри формы или диалога:
  у Next.js есть собственный служебный элемент с ролью `alert`.
- **React очищает неуправляемые поля формы после действия**, даже если оно вернуло ошибку.
  В формах с проверкой использовать управляемые поля или `defaultValue` из состояния.
- **Почты у пользователей нет.** Better Auth требует поле email — туда пишется служебный адрес
  `<логин>@users.teamboard.invalid`. Наружу его не показывать.
- **HTTP-адреса Better Auth не опубликованы** (нет `/api/auth/*`): вход и регистрация только через
  наши действия, иначе обходится ограничитель попыток. Не добавлять `toNextJsHandler`.
- **Настройки читаются при запуске, а не при сборке**: `getEnv()`/`getDb()` ленивые. Не вызывать их
  на верхнем уровне модуля. В коде страниц сначала `await headers()` / `await connection()`, и только
  потом обращение к настройкам, сервисам и базе — иначе сборка без секретов (Docker, CI) упадёт.
  Проверка: `pnpm build` без `.env.local` должен проходить.
- **`proxy.ts`** (бывший middleware) проверяет только наличие cookie — это удобство, а не защита.
- Дедлайн — строка `ГГГГ-ММ-ДД` без времени. «Сегодня» — только через `todayIso()` из `src/lib/dates.ts`
  (часовой пояс команды, `APP_TIME_ZONE`): сервер в Docker живёт в UTC, и `new Date()` «в лоб» даст
  неверную дату ночью по Москве.
- Фильтр по ответственному — `TaskFilters.assignee`: `{ kind: "member", id }` или `{ kind: "unassigned" }`.
- Смена статуса (`changeTaskStatusSchema`) — частный случай изменения: в сервисе один метод `update`.
- Адрес клиента (`RequestContext.clientIp`) — только для ограничителя попыток. Берётся последний адрес
  из `X-Forwarded-For` (его дописывает наш прокси).
- Правила границ слоёв закреплены тестами `tests/architecture/boundaries.test.ts`. Меняешь
  `eslint.config.mjs` — добавь пример в этот тест.

## Как добавить функцию (на примере задач)

1. При необходимости — поле в `src/db/schema`, затем `pnpm db:generate` (миграцию закоммитить).
2. Типы и константы — `model.ts`, проверка ввода — `schemas.ts`, права — `policy.ts` (+ тесты).
3. `server/repository.ts` — запросы; тест на базе в памяти (`tests/helpers/test-db.ts`).
4. `server/service.ts` — правила (права, «не найдено»); тест.
5. `server/index.ts` — сборка; `server/actions.ts` — `authedAction(...)`; `server/queries.ts` — чтение.
6. Компоненты в `components/`, страница в `src/app`.
7. Сквозной тест в `tests/e2e` (проекты `desktop` и `mobile`).

Готовый образец всех слоёв — модули `features/auth` и `features/users`.

## Состояние

Приложение готово и выложено (http://138.16.186.130, Docker + Caddy, см. README «Развёртывание»).
Сделано всё из ТЗ плюс канбан с перетаскиванием, приоритет, дедлайн, тёмная тема, мобильная версия.
Ещё о чём легко забыть в интерфейсе:

- `DueDateBadge` и всё, что сравнивает с «сегодня», получает `today` сверху (считается на сервере
  в `getTaskBoard`); `todayIso()` при отрисовке клиентского компонента Cache Components не пропускает.
- `Field` прячет подсказку, когда показывает ошибку. `Button` с `loading` не получает `disabled`
  (фокус остаётся), повторное нажатие блокируется внутри.
- Сквозные тесты: общие шаги в `tests/e2e/helpers.ts`; каждый тест регистрирует своего пользователя
  и метит задачи уникальной строкой — демо-данные не трогать.
- Docker-образ: тестовые файлы исключены в `.dockerignore`; после правок сборки проверять образ.
