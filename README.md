# Teamboard

Веб-приложение для управления задачами небольшой команды. Тестовое задание на позицию Vibe Coder.

**Публичная ссылка:** http://138.16.186.130 — на странице входа есть кнопка «Войти как демо-пользователь».

## Что умеет

- Создание, редактирование и удаление задач; удалить задачу может только её автор.
- Ответственный, статусы «Новая» / «В работе» / «Завершена», приоритет, дедлайн с подсветкой просроченных.
- Канбан-доска с перетаскиванием (мышь, касание, клавиатура) и табличный режим «Список».
- Поиск и фильтры по статусу, приоритету, ответственному и просроченным. Их состояние хранится
  в адресной строке, поэтому переживает перезагрузку, и ссылкой можно поделиться.
- Регистрация и вход по логину и паролю, демо-вход, сессии в базе.
- Данные хранятся в PostgreSQL и сохраняются после перезагрузки.
- Адаптивный интерфейс: на компьютере доска из трёх колонок, на телефоне вкладки, шторки и кнопка «+».
  Есть светлая и тёмная тема.
- Оптимистичные обновления, индикатор «Все изменения сохранены», отмена смены статуса из уведомления.

## Ответы на вопросы задания

### 1. Какие ИИ и инструменты использовались

- **Claude Code** (настольное приложение Claude, модель Claude Opus 5.5): архитектура, код, тесты,
  ревью, выкладка на сервер. Основной инструмент.
- **Мульти-агентный воркфлоу Claude Code**: скрипт, который запускает несколько субагентов по этапам,
  часть из них параллельно.
- **ChatGPT (генерация изображений)**: 10 вариантов внешнего вида по подготовленному промпту.
  Выбран стиль «Ясность», затем по нему сделаны 9 листов макетов (папка [`дизайн/`](дизайн)).
- Проверка результата: Vitest, Playwright, ESLint, TypeScript; скриншоты экранов сверялись с макетами.

### 2. Как задачи распределялись между агентами

Работа шла этапами, и после каждого результат проверял основной агент (оркестратор).

1. **Согласование:** вместе со мной разобрали ТЗ, выбрали стек (с учётом того, что проверяющие
   в России — никаких Vercel/Supabase/CDN) и договорились о правилах доступа.
2. **Архитектура (основной агент):** слои, база, авторизация, тесты, Docker, CI, правила для агентов
   в [CLAUDE.md](CLAUDE.md). Двое ревьюеров (код и безопасность) независимо проверили фундамент.
3. **Воркфлоу из 9 агентов** (около 80 минут):

   | Этап              | Агенты (параллельно в одном этапе)                                        |
   | ----------------- | ------------------------------------------------------------------------- |
   | Основа            | серверная логика задач · дизайн-система по макетам                        |
   | Экраны            | доска, список, фильтры, мобильная версия · окна задач, вход и регистрация |
   | Сверка с макетами | агент делал скриншоты в двух темах и на телефоне и правил расхождения     |
   | Сквозные тесты    | агент писал e2e-тесты и чинил найденные ими ошибки                        |
   | Ревью             | код и безопасность · UX и доступность (WCAG 2.2)                          |
   | Исправления       | агент проверял каждую находку, исправлял её и прогонял все проверки       |

   Чтобы параллельные агенты не мешали друг другу, у каждого была своя зона файлов. Точки стыковки
   («контракты» — провайдер окон задач и индикатор сохранения) оркестратор написал заранее.

4. **Финальная проверка и выкладка (основной агент):** повторный прогон всех тестов, сборка
   Docker-образа на сервере, проверка сайта в браузере.

### 3. Трудности и как они решались

- **Next.js 16 сильно отличается от того, что модели «помнят»**: Cache Components, `proxy.ts` вместо
  middleware, скрытые через `<Activity>` предыдущие страницы. Агенты читали документацию из
  `node_modules/next/dist/docs`, а найденные особенности записывались в CLAUDE.md для следующих агентов.
- **Параллельные агенты в одной папке**: зоны ответственности, заранее написанные контракты, запрет
  на общую сборку во время работы, коммит только своих файлов.
- **Агенты склонны «верить себе»**: каждую находку ревью сначала проверяли воспроизведением.
  Отдельный агент сверял интерфейс с макетами по скриншотам, а e2e-тесты нашли реальную ошибку
  (календарь брал фокус не на день).
- **Цвета из макета не проходили по контрасту** (серый текст 4.17:1). Цвета подправлены до нормы
  WCAG AA, а ревью доступности нашло ещё несколько мест.
- **Выкладка из России**: Docker Hub с сервера не отвечал — настроены зеркала. Сборка Docker-образа
  до этого ни разу не запускалась (на рабочей машине нет Docker) и упала на тестовых файлах — это
  исправлено в `.dockerignore`. Вывод: проверять нужно сам сценарий выкладки, а не только тесты.
- **Безопасность**: подделка адреса клиента через `X-Forwarded-For`, утечка параметров запросов
  в журнал, неатомарные демо-данные — найдено ревью и исправлено. Подробнее в [docs/DEVLOG.md](docs/DEVLOG.md).

### 4. Что можно улучшить при наличии времени

- Домен и HTTPS: сейчас сайт работает по IP и HTTP. Caddy уже стоит, и для HTTPS нужно поменять одну
  переменную `SITE_ADDRESS`.
- Обновление доски у всей команды в реальном времени (SSE/WebSocket) и защита от одновременного
  редактирования (версия записи).
- Комментарии, история изменений задачи, вложения, уведомления ответственному.
- Несколько команд и роли (администратор, участник), приглашения, восстановление пароля.
- Ручной порядок карточек внутри колонки и пагинация для больших команд (сейчас до 500 задач).
- Мониторинг и резервные копии базы, CI с выкладкой на сервер.

## Стек

Next.js 16 (App Router, Cache Components) · React 19 · TypeScript (strict) · Tailwind CSS 4 ·
Radix UI · dnd-kit · PostgreSQL · Drizzle ORM · Better Auth · Zod · Vitest + PGlite · Playwright ·
Docker · Caddy

Браузер не обращается ни к каким сторонним сервисам: шрифт и иконки поставляются вместе с приложением.

## Качество

- 337 модульных и интеграционных тестов, покрытие кода — около 95 %. Интеграционные тесты работают
  на PostgreSQL в памяти (PGlite).
- 27 сквозных сценариев Playwright, каждый на двух устройствах (компьютер и Pixel 7): задачи, права,
  перетаскивание, фильтры в адресе, тема, отсутствие горизонтальной прокрутки.
- Границы слоёв проверяет линтер, а сами правила закреплены 41 тестом.
- Проверка ввода на сервере (Zod), права проверяет сервис, ограничение частоты попыток входа
  и изменений, CSP и заголовки безопасности.

## Быстрый запуск (Docker)

```bash
cp .env.example .env        # заполнить AUTH_SECRET, POSTGRES_PASSWORD, APP_URL
docker compose up -d --build
```

Приложение откроется на `http://localhost:3000`. Миграции базы применяются автоматически при старте.

## Запуск без Docker

Нужны Node.js 22+, pnpm и PostgreSQL.

```bash
pnpm install
cp .env.example .env.local  # заполнить DATABASE_URL, APP_URL, AUTH_SECRET
pnpm dev                    # разработка
# или боевой режим:
pnpm build && pnpm start
```

## Настройки

| Переменная       | Обязательна   | Описание                                                     |
| ---------------- | ------------- | ------------------------------------------------------------ |
| `DATABASE_URL`   | да            | Строка подключения к PostgreSQL                              |
| `APP_URL`        | да            | Публичный адрес приложения                                   |
| `AUTH_SECRET`    | да            | Секрет сессий, от 32 символов: `openssl rand -base64 32`     |
| `RUN_MIGRATIONS` | нет (`true`)  | Применять миграции при старте                                |
| `SEED_DEMO_DATA` | нет (`false`) | Заполнить пустую базу демо-данными                           |
| `DEMO_PASSWORD`  | нет           | Пароль демо-аккаунтов; включает кнопку «Войти как демо»      |
| `SITE_ADDRESS`   | нет (`:80`)   | Только для Caddy: домен (тогда будет HTTPS) или `:80` для IP |

С неверными настройками сервер не запустится и напишет в журнал, что именно не так.

## Демо-доступ

При `SEED_DEMO_DATA=true` и заданном `DEMO_PASSWORD` в пустой базе создаются участники
`anna`, `olga`, `maxim`, `dmitry` и набор задач. На странице входа появляется кнопка
«Войти как демо-пользователь».

## Проверки

```bash
pnpm check      # типы, линтер, формат, тесты с покрытием
pnpm test:e2e   # сквозные тесты в браузере (нужна база teamboard_e2e)
```

## Развёртывание на сервере

```bash
cp .env.example .env   # заполнить секреты, APP_URL и SITE_ADDRESS
docker compose -f docker-compose.yml -f deploy/compose.caddy.yml up -d --build
```

Caddy принимает запросы на портах 80/443 и передаёт их приложению. Если в `SITE_ADDRESS` указан домен,
Caddy сам получает HTTPS-сертификат. Порт приложения наружу не открывается.
Проверка работоспособности: `GET /api/health` → `200 {"status":"ok"}`.

На серверах в России Docker Hub может не отвечать — тогда в `/etc/docker/daemon.json` нужно указать
зеркало (`"registry-mirrors": ["https://mirror.gcr.io"]`).
